# 3D for SuperDes — design (2026-11-26)

## Intent
Clients understand a 2D plan poorly. A 3D view of their own plan, with their own finishes, makes the design
tangible and makes renders and the dossier more useful. The owner asked for all six 3D features, built in stages,
each on its own branch with a PR to JonathanZouari/OwnDesign.

## Scope decision
The PRD lists "interactive 3D model navigation / 360° walkthroughs" as out of scope for the MVP. The owner
approved adding them (2026-11-26). Everything stays **conceptual**: no structural accuracy claims.

## Goals (stages)
1. **3D view** of the plan: walls raised with door/window holes, floors per room, furniture and fixtures as boxes at
   real sizes; orbit, zoom, top view. Live: shows the editor's current (also unsaved) geometry.
2. **Finishes in 3D**: chosen floor/wall finish colours on the surfaces.
3. **Walk-through**: eye-height (1.6 m) first-person mode; keyboard/mouse on desktop, drag + on-screen buttons on
   touch; cannot walk through walls.
4. **Render camera from 3D**: "Use this view for a render" sends the 3D camera pose with a render request; the concept
   renderer draws from that pose (perspective from the given point and direction).
5. **3D in the dossier**: "Add 3D views to dossier" captures snapshots and stores them as project uploads the dossier
   includes.
6. **Move furniture in 3D**: drag furniture/fixtures on the floor in 3D. The 2D editor stays the single source of
   truth: the 3D view calls the editor's own move path (undo, dirty state, Save version unchanged).

## Non-goals
Textures/photoreal materials, lighting simulation, editing walls/rooms in 3D, VR, ceilings (left open so the
top view works), multi-storey.

## Anti-goals
- Two sources of truth for the plan.
- 3D library loaded on pages that don't use it (it is ~720 KB).
- Breaking the CSP (`script-src 'self'`): no CDN, no inline import map.

## Approaches
- **Three.js, vendored (chosen).** Mature, MIT, has orbit and pointer-lock controls. Self-hosted under
  `frontend/static/js/vendor/three/` (v0.180.0), lazy-loaded with `import()` only when 3D opens. Controls' bare
  `'three'` import rewritten to a relative path (no import map needed).
- Babylon.js: heavier, no gain here. Rejected.
- Hand-written WebGL / CSS 3D: far more code for less. Rejected.

## Design
- `frontend/static/js/editor/scene-model.js`: pure function `sceneModel(geometry, {finishes, wallHeight})` → plain
  data (wall pieces split around openings, room floor polygons, item boxes with colours). No Three.js, unit-tested
  with `node --test`.
- `frontend/static/js/editor/view3d.js`: `View3D` class (mount, update(model), setMode('orbit'|'walk'),
  topView(), snapshot() → data URL, cameraPose(), onDragItem callback, dispose()). Imports Three.js lazily.
- Plan tab: a **2D / 3D** switch in the editor toolbar; 3D replaces the SVG canvas area. Editor `onChange` rebuilds
  the scene. Units: mm in the plan → metres in 3D; plan y (down) → 3D z.
- Wall height default 2600 mm (same as the concept renderer). Doors 2100 mm high; windows 900–2100 mm.
- Wall colour: the wall finish of the room whose polygon is nearest the wall's midpoint; otherwise neutral.
- Stage 4: render API accepts an optional `camera` `{x, y, yaw}` (mm, degrees), validated; concept renderer uses it.
- Stage 5: snapshots uploaded through the existing uploads API with kind `3d-view`; dossier shows them.
- Stage 6: `PlanEditor.moveItem(type, id, x, y)` (push undo, set, changed) — the 3D drag calls it on drop.
- UI uses the existing button and toolbar styles (no new visual language).

## Testing
Unit: scene model (openings, empty plan, rotation, finishes, huge plan limits). Browser: Playwright on a local
copy — 3D opens, renders pixels, no console errors, orbit/walk/drag work, phone size. Regression: full backend
suite + click test. Security: no new inputs except stage 4 camera (validated) and stage 5 uploads (existing checks).
